Braid nRF24L01+ link (PACKET carrier) - bench notes
========================================================

What it is: a third transport next to ESP-NOW and the UART link. Spec 1.2
nRF24 row, 11.3, 11.6, 11.11, 12.4, Appendix C.5 (design) and C.6 (pins).
32-byte Enhanced ShockBurst payloads, link-local segmentation so the node
still sees max_frame 250 (path MTU unchanged), ESB auto-ACK unicast on
unit-ID-derived 5-byte addresses, NO_ACK broadcast pipe for floods, fixed
link cost 2, no RSSI.

NOT YET RUN ON HARDWARE: no module was attached when this was written (the
user may not own nRF24 modules yet). The register driver is build-only; the
segmentation layer, the register sequence and the adapter are host-tested
(firmware/test/host/test_nrf24_link.c, 347633 checks). Wired into
node_app, the console and the build (see 6 for what was done and what was
not). Treat every "expected" line as the target.

2. Wiring
---------

Module: nRF24L01+ (8-pin 2x4 header). 3.3 V ONLY on VCC (5 V kills it); SPI
pins accept 3.3 V logic (the ESP32 is 3.3 V anyway). Put 10 uF (plus 100 nF)
directly across the module's VCC / GND pins: the chip draws 11-13 mA bursts
in TX and brown-outs without it (the number one cause of "works on the bench,
dies in the field"). The PA+LNA variant draws up to 115 mA on transmit and
needs its own 3.3 V regulator (an AMS1117-3.3 fed from 5 V, 10 uF + 100 nF at
the module), never the dev board's 3.3 V pin; keep its antenna away from the
ESP32 antenna (12.4: separated or cross-polarised).

Default pins (spec C.6 pin plans, IO_MUX pins of the SPI controller used;
hal_nrf24_default_cfg() fills them):

    signal   ESP32-WROOM-32E       ESP32-S3-WROOM-1 / -1U
    SCK      GPIO18 (VSPI)         GPIO12 (SPI2 / FSPI)
    MISO     GPIO19                GPIO13
    MOSI     GPIO23                GPIO11
    CSN      GPIO5  (see note)     GPIO10
    CE       GPIO4                 GPIO9
    IRQ      GPIO35 (optional)     GPIO14 (optional)   default: not used (polling)
    VCC      3.3 V                 3.3 V
    GND      GND                   GND

    // STRAPPING: GPIO5 (ESP32 CSN) must be high at boot (SDIO slave timing
    // strap). CSN idles high: most dev boards have a pull-up on GPIO5 and
    // the SPI controller drives it high after init, so the strap is
    // satisfied. Do not move CSN to GPIO0 / 2 / 12 / 15.
    // GPIO35 is input only: fine for the IRQ (active low, the module drives
    // it push-pull; 34-39 have no internal pulls, which is why the default
    // is polling: an IRQ input configured without the wire floats and
    // storms. Set nirq=35 / 14 only when the wire is there).

    No collision with led=2, btn=0, the UART link (ESP32 17/16, S3 17/18),
    S3 octal PSRAM 33-37 or USB 19/20. S3: none of the pins is strapping.
    port_nrf24.cpp refuses flash pins (ESP32 6-11, S3 26-32), S3 33-37 and
    19/20, strapping pins for CE / CSN other than GPIO5 CSN, and input-only
    pins as outputs.

SPI: mode 0, MSB first, 8 MHz default (10 MHz max per datasheet; 4 MHz on
flying leads > 10 cm). CSN is driven by the SPI controller: low for the whole
command, high between commands (required by the chip). The transaction is a
polling one without DMA (33 bytes max), so the protocol task blocks for a
few tens of microseconds per command.

IRQ vs polling: the IRQ pin is optional and off by default. Without it the protocol task polls
STATUS every 2 ms (cfg.poll_us) while listening and every 0.5 ms while a
frame is in flight; with it, the ISR posts an event to the "br" queue and
the pump runs at once. The RX FIFO is only 3 payloads deep; a neighbour's
auto-ACK segments are retried by its ESB for ARC 15 x ARD 500 us = 7.5 ms,
so the pump must run at least every ~5 ms while listening. Polling at 2 ms
is enough; the IRQ lowers latency (one segment per wake-up instead of per
poll) and is recommended for throughput.


3. Radio settings
-----------------

    channel     76 default; 76..81 at 2 Mbps (2476-2481 MHz, above Wi-Fi
                channel 13 and inside the 2483.5 MHz ISM limit). 82..83
                only at 250 kbps / 1 Mbps (a 2 Mbps signal spills past
                2483.5 MHz). The adapter accepts 0..125 but the console
                should refuse outside 76..83 (C.5).
    rate        2 Mbps (C.5); 1 Mbps / 250 kbps selectable (250 kbps gives
                about 9 dB more link budget at 1/8 the throughput).
    PA          0 dBm (max) default; -6 / -12 / -18 dBm for bench use
                (two modules 20 cm apart at 0 dBm overload each other:
                use PA min on the bench or put 1 m between them).
    CRC         2 bytes (EN_CRC | CRCO), ESB requirement for auto-ACK.
    DPL         dynamic payload length on pipes 0 and 1; RX_PW_Px = 32 as a
                fallback.
    EN_AA       0x03: auto-ACK on BOTH pipes, broadcast included. The
                datasheet requires EN_AA on a pipe for dynamic payloads on
                it; a flood is not acknowledged because the transmitter
                writes it with W_TX_PAYLOAD_NO_ACK (FEATURE.EN_DYN_ACK),
                which sets the NO_ACK flag in the packet so no receiver
                replies (C.5 "Floods use W_TX_PAYLOAD_NOACK").
    SETUP_RETR  ARD 500 us (code 1), ARC 15 (C.5): 16 attempts, 7.5 ms.
    SETUP_AW    5 bytes.
    Addresses   unit U: 50 4C U_hi U_lo A5 (pipe 0, own); broadcast
                50 4C FF FF A5 (pipe 1). TX_ADDR and pipe 0 are set to the
                destination for a unicast (the ACK comes back on pipe 0, as
                RF24 does) and pipe 0 is restored to own when listening.
                Byte order on the bus: see 8 (SPEC-NOTES candidates).

Coexistence with the ESP-NOW mesh (12.4): mesh channel 1-6 (2412-2437 MHz),
nRF channel 76-81 (2476-2481 MHz): > 39 MHz apart. Antennas separated or
cross-polarised. A bridge (both radios on one board) must not start a
transmission on one radio while the other is mid-reception of a multi-
segment frame: nrf24_link_radio_busy() is that hook for the nRF24 side
(true while transmitting and for 1 ms after the last segment received);
the ESP-NOW side uses hal_radio_tx_inflight() (own TX only; ESP-NOW
reception is invisible to the app). Cross-radio arbitration is implemented:
firmware/RADIO-ARB.txt (SPEC-NOTES N62-N64; the nRF24 transmit gate is
nrf24_link_set_tx_gate()). Commissioning test: compare crc_fail / reassembly drops /
rx_frames at the bridge with the other radio idle and loaded.


4. Segment format and reassembly (C.5, as implemented)
-------------------------------------------------------

ESB payload, 3..32 bytes:

    byte 0   src        low byte of the transmitter's unit ID
    byte 1   tag        per-transmitter frame counter, +1 per frame, wraps
    byte 2   bit 7      LAST (1 on the final segment)
             bits 6..0  idx (0 for the first segment)
    3..31    payload    exactly 29 bytes on every segment except LAST
                        (0..29 on LAST)

    frame of n bytes -> ceil(n / 29) segments, 9 for 250 bytes; an empty
    frame is one LAST segment of 3 bytes. 250 frame bytes = 8 x 32 + 21 =
    277 payload bytes (1.1x, payload only); with preamble, address, PCF,
    CRC and the ACKs per packet C.5's "about 1.5x on the air" holds, about
    9 x 0.4 ms = 3.6 ms per frame at 2 Mbps with an IRQ-driven pump.

Reassembly: one buffer per neighbour keyed by src (NRF24_SEG_SLOTS_DEFAULT
4, up to 8), opened by idx 0, segments in order. Dropped whole and counted
on: a gap (idx not the next one: gaps), another tag from the same src
before LAST (foreign_tag), 50 ms without a segment (timeouts), > 250 bytes
(oversize), segment 0 from a new src when every buffer is busy
(buffer_full). Segments with idx > 0 and no open frame from that src are
counted per segment as orphans (the tail of a dropped frame, or a frame
whose segment 0 was lost: that frame leaves no other record). A repeat of
the last accepted segment (same src, tag, idx) is ignored and counted as a
dup; a LAST repeat after completion too (the ESB PID filter normally drops
those in hardware, software sees them after a chip reset or on a NO_ACK
copy). Two neighbours whose unit IDs share a low byte interleave into one
buffer and the frame CRC in the node drops both (C.5 known limitation).

Counters: adapter nrf24_link_stats_t (tx_queued, tx_frames, tx_unicast,
tx_bcast, tx_segments, tx_refused, tx_bad_len, tx_max_rt, tx_stuck,
tx_radio_err, tx_deferred, tx_status_ok / fail, rx_segments, rx_frames,
rx_admit_drop, rx_src_mismatch, rx_bad_pipe, rx_radio_err) and reassembly
nrf24_seg_stats_t (seg_tx, seg_rx, frames_tx, frames_rx, tx_refused,
timeouts, gaps, orphans, foreign_tag, dups, malformed, oversize,
buffer_full, frames_dropped). The spec's seg_fail (br_stats_t) is NOT
incremented: the core has no hook for an adapter counter (see 6 and 8).


5. Transmit / receive behaviour (nrf24_link.c)
----------------------------------------------

- send() queues the frame (4 frames x 250 bytes) and returns at once;
  BR_ERR_QUEUE_FULL when full (the frame is lost and counted).
- nrf24_link_pump(l, node, now_us) from the protocol task, outside any
  br_node_* call: drains the RX FIFO into reassembly (each frame goes
  br_transport_admit -> br_node_rx with the hint {address derived from the
  header prev_hop, addr_len 5, rssi -128}), expires reassembly buffers, and
  runs the half-duplex transmit state machine: leave PRX, program the
  destination, send the segments one at a time (TX_DS -> next; MAX_RT ->
  FLUSH_TX, clear, frame abandoned, br_node_tx_status(delivered = false);
  all TX_DS -> delivered = true), back to PRX, guard 2 ms (C.5 NRF_GUARD_MS)
  before the next frame. A frame with no TX_DS / MAX_RT within 20 ms is
  abandoned as "stuck" (chip or CE wire fault) and reported undelivered.
  Broadcast frames go W_TX_PAYLOAD_NO_ACK and report nothing (1.2).
- Collision avoidance (ESB has no carrier sense): the pump does not start a
  frame within 1 ms (cfg.rx_hold_us) of the last segment received, open
  frame or just completed. Open: the neighbour is mid-frame to us (12.4).
  Just completed: when our hardware ACK for its LAST segment was lost the
  neighbour retransmits it after ARD 500 us, and only a PRX acknowledges
  the repeat; replying at once would put both radios in PTX, both deaf,
  until MAX_RT on both sides (seen in the host test before the hold was
  added). The hold is shorter than the guard, so a reply always starts
  inside the peer's guard and its first segment opens a buffer at the peer
  before the peer's next frame is due. Two lost ACKs in a row still give a
  head-on start and a MAX_RT pair; 11.6 counts it (3 consecutive delete the
  link).
- The pump returns the time it wants to run again (guard end, next status
  poll, reassembly timeout, or now + poll_us): the task's queue wait should
  be capped at that deadline.

7. Host test (firmware/test/host/test_nrf24_link.c)
---------------------------------------------------

Part A, segmentation: header layout (src / tag / idx|LAST / 29-byte
payload, 9 segments for 250, tag increments, empty frame = 3 bytes); round
trip of every size 0..250 and of the A.3 SEEK frame and the A.15 SEEK and
HELLO frames; each of the 9 segments of a 250-byte frame dropped (LAST lost
-> timeout path), duplicated (ignored), swapped with its neighbour (gap);
whole frame repeated; two transmitters with distinct src bytes interleaved
segment by segment; a foreign tag before LAST; the 50 ms timeout mid-frame;
buffer-full with 2 slots and three neighbours, LRU reuse of idle slots,
stale open buffers reclaimed by the timeout only; malformed segments and
oversize.

Part B, register driver over a register-model fake of the SPI bus: the
init sequence (CONFIG 0x0C then 0x0E with PWR_UP last, FEATURE 0x05, DYNPD
0x03, EN_AA 0x03, EN_RXADDR 0x03, SETUP_AW 0x03, SETUP_RETR 0x1F, RF_CH 76,
RF_SETUP 0x0E for 2 Mbps / 0 dBm, RX_PW_Px 32, FLUSH_TX, FLUSH_RX, STATUS
cleared before PWR_UP, CE low throughout, power-up waits); 250 kbps / 1
Mbps / PA codes; argument checks; the ACTIVATE 0x73 fallback for non-plus
parts; no chip wired -> NO_CHIP; address byte order (C.5 list in, LSByte
first on the bus) for pipes 0 / 1 / 2; TX_ADDR + pipe 0 programming and
restore on listening; W_TX_PAYLOAD vs W_TX_PAYLOAD_NO_ACK, FIFO full after
3; CE pulse; MAX_RT recovery (FLUSH_TX, flag cleared, FIFO empty); payload
reads with pipe / width, width > 32 flushes; channel change; power down /
up; raw register access; bus failure -> SPI error, STATUS invalid.

Part C, adapter: transport fields (PACKET, 250, rs 0, broadcast, mac_retry,
cost 2, addr_len 5), register() fills BR_NODE_MAX_TRANSPORTS slots then
BR_ERR_TOO_BIG, send() refusals; MAX_RT -> br_node_tx_status(delivered =
false) with 16 attempts 500 us apart (7.5 ms), FLUSH_TX + clear, back to
PRX, guard; broadcast frames report nothing; queue full (4); the 12.4 busy
hook (busy for 1 ms after a segment, transmit deferred then released); a
stuck radio (no TX_DS) abandoned after 20 ms. Then two real br_node
instances (sender 0x0101 -> group 0xFF10, probe 0x0103; bench key, AUTH on,
fec_m 0, ARQ on, demo MODE) through two adapters on a fake ESB medium that
delivers 32-byte payloads with per-attempt loss, honours auto-ACK (ARC
retries 500 us apart, PID duplicate filter, MAX_RT, payload kept until
abort), NO_ACK, and a radio in PTX hearing nothing:
  - clean: SEEK -> HELLO -> BIND -> MODE -> STREAMING, 20 presses (40 DATA)
    all acknowledged, no MAX_RT, no reassembly drop, frame counts match end
    to end, the SEEK leaves with path_mtu 250, floods NO_ACK, the probe's
    link table holds the sender's derived address 50 4C 01 01 A5 with RSSI
    unknown;
  - 5 % segment and ACK loss with ESB auto-ACK (ARC 15), loss from the
    first frame, 6 seeds: every press acknowledged, at most 2 MAX_RT per
    run (the two-lost-ACKs head-on case), no 11.6 link deletion; the
    reassembly drops seen are flood segments;
  - 5 % segment loss with the ACK blind (an unacknowledged carrier: every
    lost segment is a lost frame), armed once STREAMING, 6 seeds: every
    DATA accounted for (all 40 acknowledged in every seed, ARQ retx 3..17),
    reassembly drops and orphans counted, session still STREAMING;
  - the probe's allowlist excluding the sender: nothing reaches the core.
Result: 347633 checks, 0 failed, normal and -DBR_SANITIZE=ON trees.

Former core defect, fixed: a lost first MODE frame used to stall the
probe's ARQ window; SPEC-NOTES N46 ("DATA floor") removed it and
test_scen_mode_loss.c covers it. The ACK-blind run still arms loss only once

run measures.


8. SPEC-NOTES candidates (C.5 left these undefined; decisions taken here)
-------------------------------------------------------------------------

 N46  C.5 "idx:7 | LAST:1": LAST is bit 7 of byte 2, idx bits 6..0.
 N47  C.5 "ceil(n / 29) packets" is 0 for n = 0: an empty frame goes as one
      LAST segment with no payload (3 bytes). The adapter never sends one
      (send() refuses len 0, BR_ERR_ARG, like uart_link).
 N48  Duplicates: a repeat of the last accepted segment (same src, tag,
      idx), or of a completed frame's segments, is ignored and counted
      (dups); every other idx mismatch drops the open frame (gaps). C.5
      says only "segments in order; a gap ... drops the frame".
 N49  Segments with idx > 0 and no open frame are counted per segment as
      orphans, not as frame drops (a frame whose segment 0 was lost has no
      other record); seg_fail-style totals are frames_dropped + orphans
      of segment 1, which the adapter cannot tell apart.
 N50  Buffer-full policy: a segment 0 from a new src when every buffer is
      open is dropped (buffer_full); open buffers are reclaimed only by the
      50 ms timeout, idle (closed) ones by LRU. C.5 names 4 buffers but no
      policy.
 N51  Address byte order: C.5 lists "50 4C U_hi U_lo A5"; the chip takes
      address registers LSByte first. The listed order is the on-air order
      (index 0 = most significant, sent first after the preamble); the
      driver writes the bytes reversed (A5 U_lo U_hi 4C 50). All nodes must
      agree or nobody hears anybody; an RF24-library peer would call
      openWritingPipe(0x504C0101A5ULL) for unit 0x0101.
 N52  EN_AA stays set on the broadcast pipe (datasheet: dynamic payloads on
      a pipe require ENAA_Px); floods are unacknowledged through the
      per-packet NO_ACK flag (W_TX_PAYLOAD_NO_ACK), which C.5 already
      names. "NO_ACK broadcast pipe" means that, not EN_AA cleared.
 N53  Segment src byte vs header prev_hop: the hint address is derived from
      the header prev_hop (bytes 6..7), not from the src byte; a mismatch
      is counted (rx_src_mismatch) and the frame is still delivered (the
      CRC / hop_tag decide).
 N54  seg_fail (br_stats_t, Appendix B) cannot be incremented by an
      adapter: no core hook. Proposed br_node_count_seg_fail(); until then
      the adapter's frames_dropped / orphans are the bench counters.
 N55  Half-duplex collision avoidance beyond C.5's NRF_GUARD_MS 2: a 1 ms
      post-RX hold before starting a transmit (open frame or just
      completed), see 5. Not in the spec; it removed the systematic MAX_RT
      pair after a lost ACK on a LAST segment in the host model.
 N56  C.5 "MAX_RT after the retries is the 11.6 failover signal": applied
      per frame (the frame is abandoned at the first MAX_RT segment,
      remaining segments are not sent); a frame that was fully received
      but whose last ACK was lost is reported undelivered while the peer
      has it whole (the node's dedup handles the retransmission).
 N57  12.4 "radio busy" hook: nrf24_link_radio_busy() = transmitting or
      within the 1 ms post-RX hold. ESP-NOW has no mid-reception signal;
      cross-radio arbitration is implemented in RADIO-ARB.txt (N62-N64)
      on what each radio can observe.
 N58  C.5 "NRF_REASM 4 buffers of 258 bytes": the buffers are 250 bytes
      (= max_frame); a frame that would exceed 250 is dropped as oversize
      when the segment arrives, so 258 is never needed (9 x 29 = 261 would
      be the natural capacity, 250 is the protocol limit).


9. What cannot be verified without modules
------------------------------------------

- That the chip answers at all on these pins (MISO wiring, 3.3 V, the
  presence check in hal_nrf24_init), SPI mode 0 timing at 8 MHz with the
  ESP-IDF polling driver, the CS behaviour (CSN high between commands).
- The address byte order decision N51: the host fake only checks that the
  driver reverses the bytes; whether two real modules hear each other with
  it is a two-module test. An RF24-library sketch on any Arduino with
  openReadingPipe(1, 0x504CFFFFA5ULL) on channel 76, 2 Mbps, DPL on, 2-byte
  CRC should receive our floods.
- ACTIVATE on clones (SI24R1 and friends need it, have different RF_SETUP
  power bits, and some lack dynamic payloads).
- Real ESB timing: ARD 500 us (C.5) is comfortably above the 250 us the
  datasheet allows for a 32-byte payload without ACK payload at 2 Mbps;
  whether 7.5 ms of retries covers a 9-segment frame plus the 2 ms guard
  with the real pump cadence (polling at 2 ms: about 9 x 2 = 18 ms per
  frame, so the IRQ pin matters there).
- RX FIFO depth 3 vs pump cadence: whether a 2 ms poll ever lets the FIFO
  fill (then the chip stops acknowledging and the sender retries, visible
  as acks_lost at the sender and dups at nobody).
- The 12.4 coexistence numbers (crc_fail / reassembly drops with the
  ESP-NOW radio idle vs loaded on one board), and the antenna separation.
- Current draw and brown-out with and without the 10 uF.
- The node_app wiring of 6 on real hardware: BRNRF init line, pump cadence
  with the real SPI timing, the IRQ path (ISR -> kEvtNrfIrq -> pump), the
  `nrf=on` boot with no module attached (expected: "BRNRF no module
  answering ...", board runs on its other transports).

Compile verification done instead (no hardware):

  && ctest -R nrf24: PASS; same with -DBR_SANITIZE=ON (build-asan): PASS.
- target: pio run -e esp32_dev (after rm -rf .pio/build/esp32_dev) and
  -e esp32s3_dev build components/app_nrf24_link with -Wall -Wextra

10. Other carriers
------------------

The same image carries four transports, each enabled per board from the
console and registered in this order (each present one takes the next
transport index; BRSTART lists them as transports=espnow+uart+udp+nrf24):

    espnow   on by default (`espnow=off` only on a LAN-side UDP board, 12.4)
    uart     `uart=on`   UART-LINK.txt   RAW, COBS + RS(8), point to point
    udp      `udp=on`    UDP-LINK.txt    PACKET, WiFi station + lwIP UDP, LAN side
    nrf24    `nrf=on`    NRF24-LINK.txt  PACKET, nRF24L01+ with segmentation

Policy (node_console.c, host test test_console_links.c): udp=on requires
espnow=off (a station follows the AP's channel); at least one transport
must be on; the bench allowlist `nbr=` applies to every transport by unit
ID. Expected log lines common to all carriers: BRBOOT started ... uart=yes|no
udp=yes|no nrf=yes|no, BRSTART ... transports=..., BRLINK neighbour 0x....
via=uart2|udp a.b.c.d:port|nrf24 50:4c:.. and the per-carrier BRSTAT fields
(uart_* / udp_* / nrf_*) with drop names u_* / ud_* / n_*, present only
when that link is on. FLASH-DEMO.md section 5 has the ESP-NOW-only lines.
